# Issue #37: 32x6 vs 32x7 for B4 and S1-S5: settle inside one launch

GitHub: https://github.com/JieGH/RVV_code_gen_via_MLIR_xDSL/issues/37

**Role / Label:** `needs-triage` — from the #31-#34 audit report ([issues-31-34-brief.pdf](https://github.com/JieGH/RVV_code_gen_via_MLIR_xDSL/blob/pure-xdsl/.scratch/reports/issues-31-34-brief.pdf)), next step 3. Low priority.
**Performance results per test:** Appendix A of the audit report, rows 8, 20 and 21 (B4 NR sweep; 32x6 runs; run-to-run spread).
**Status:** ✅ Settled 2026-09-28 (see §Done). **Decision: keep `32x7`.**

## Question
Is `32x6` really faster than the shipped `32x7` for B4 (and for the square shapes S1-S5)?

## What is known
- #32: 32x6 ahead of 32x7 in 8 of 8 pairs, by 0.5-3.3%, all on **core 0**.
- #34: on core 4, 32x7 ahead by 6%; on core 2, 32x6 ahead by 1%.
- The same binary moves 1-5% between launches. So today the two tiles are tied within noise.
- Both tiles are within the 32-register limit (32x6: 28 live, 32x7: 32 live); only 32x8 (36) falls off.

## Proposed work (done)
Both tiles in **one** launch, repeated over several launches, on a non-zero core, for B4 and S1-S5. Decide only if one tile wins in every launch.

## Done (2026-09-28)
New files: `config_issue37_nr6_vs_nr7.json` (two pinned rows, `[32,7]` and `[32,6]`, `skip_ref_run=true`,
`iterations=5`) and `datasets/issue37_b4_square_32x6.dat` (B4 + S1-S5, the same shapes as the shipped
`issue2_square_bert_32x7.dat`, so both tiles are compared on identical M/N/K). One `compile_macro_bench.sh`
launch already builds and runs both rows back to back (each its own `pj_gen/` dir), satisfying "both tiles
in one launch"; that same config was then run **3 times** per the #39 house rules (core 4, `--no-nc-overrides
--cpu 4 --tmin 10`, reference protocol), with a board check for other users' processes before each launch
(board was clear all three times).

**Result: 32x7 wins all 6 cases (B4, S1-S5) in all 3 launches — 18/18.** Not a near-tie: the margin is
3.7-8.7% on the 3-launch average, well outside the ~3% house-rules noise threshold, and every individual
launch shows the same ranking (unlike #32, which read a 0.5-3.3% gap off 8 pairs run entirely on core 0 —
now known to run 5-10% slower per the #39 audit, which likely explains why that gap pointed the other way).

3-launch average GOPs (mean-time == median-rep in every case here; std-dev/median was 0% or 1% throughout,
so the two metrics do not diverge):

| Case | Shape | 32x6 (avg GOPs) | 32x7 (avg GOPs) | 32x7 margin |
|---|---|---|---|---|
| B4 | 4096x384x1024 | 7.80 | 8.09 | +3.7% |
| S1 | 1000x1000x1000 | 8.32 | 8.90 | +7.0% |
| S2 | 2000x2000x2000 | 8.46 | 9.20 | +8.7% |
| S3 | 3000x3000x3000 | 8.73 | 9.39 | +7.6% |
| S4 | 4000x4000x4000 | 8.65 | 9.22 | +6.6% |
| S5 | 5000x5000x5000 | 8.83 | 9.53 | +7.9% |

Per-launch numbers (mean-time GOPs; median-rep matched to within 0.01 GOPs in every row):

| Case | Launch 1 (32x6 / 32x7) | Launch 2 (32x6 / 32x7) | Launch 3 (32x6 / 32x7) |
|---|---|---|---|
| B4 | 7.71 / 8.14 | 7.87 / 7.96 | 7.82 / 8.16 |
| S1 | 8.30 / 8.89 | 8.31 / 8.91 | 8.34 / 8.89 |
| S2 | 8.41 / 9.22 | 8.44 / 9.23 | 8.54 / 9.15 |
| S3 | 8.73 / 9.46 | 8.72 / 9.34 | 8.74 / 9.38 |
| S4 | 8.65 / 9.28 | 8.61 / 9.16 | 8.68 / 9.21 |
| S5 | 8.80 / 9.61 | 8.86 / 9.45 | 8.82 / 9.52 |

S3-S5 at 32x6 fit only 1-2 reps in `tmin=10s` in launch 1 (near-single cold samples, flagged `[WARN]` in
that run's log); the same shapes at 32x6 got more reps in launches 2-3 and the ranking did not change, so
this does not affect the decision.

Logs (all three launches, committed): `tests/pure_xdsl_blis_rvv/logs/run_2026-09-28_113634/`,
`run_2026-09-28_114331/`, `run_2026-09-28_115034/` — board `jbpi2`, core 4, `UNINSTRUMENTED` build,
reference protocol, `--no-nc-overrides`.

**Decision: no change to the shipped configuration.** `32x7` stays pinned for B4 and S1-S5 in `config.json`;
`config_issue37_nr6_vs_nr7.json` and `issue37_b4_square_32x6.dat` are kept for anyone who wants to rerun
this comparison later.
