## 1. What's being asked

The user noticed that the `16x16` and `24x10` kernel shapes appear to run into register pressure, and
suspects the xDSL code generator is producing a kernel that over-utilizes registers "just a bit."
They want, for a fixed 2048×2048×2048 fp32 GEMM:

- Both designs' kernels at these two shapes run and compared, including the packing step — this
  project's vector pack **and** its scalar pack, against the reference's one (scalar) pack.
- Reference and xDSL kernel **source code** compared side by side at each shape.
- A performance evaluation, with **assembly-level analysis** to check the register-spilling
  suspicion directly (not just reasoned from a formula), since past work in this project only ever
  reasoned about spilling from tile-shape arithmetic without reading generated assembly for more than
  one shape.

This is a diagnostic plan only — no fix or redesign is in scope here (that mirrors [[0016]] §4.4's
same boundary: root-cause first, redesign later, separately).

## 2. What's already known, so this plan doesn't re-derive it (read-only, done now)

**Neither shape exists on the xDSL side yet.** `16x16` is a commented-out `config.json` row from a
pre-reference-protocol era; `24x10` doesn't exist in the current schema at all. Both need new,
dedicated config rows before there is anything to benchmark or disassemble on this project's side.

**The static register formula differs between the two designs, and by a lot — this is the main
thing this plan needs to pin down, not assume.** This project's packed design (compute nest
consumes one broadcast B scalar per column at a time) follows `(MR/8)×(1+NR) ≤ 32`
([[0017]] §2):

| shape | `MR/8` | our formula: `(MR/8)×(1+NR)` | spare |
|---|---|---|---|
| 16x16 | 2 | 34 | −2 (over) |
| 24x10 | 3 | 33 | −1 (over) |

But the reference's `RVV_256_LDX/fp32` kernels do **direct, unpacked, strided loads** (no pack
step at all inside the kernel tree) and — at least in the `loadAB/bcast` variant read for this plan
— keep a full row of B broadcast registers live simultaneously alongside the C accumulators:

| shape | reference (`loadAB/bcast`) live v-regs | spare |
|---|---|---|
| 16x16 | 16 B + 16×2 C + 2 A = 50 | −18 (badly over) |
| 24x10 | 10 B + 10×3 C + 3 A = 43 | −11 (over) |

If that count is representative, the reference is **far** more over-budget than our own design at
these two shapes — the opposite of the user's suspicion that our design is the one over-utilizing.
But `bcast` is only one of six load/broadcast variants the reference ships per shape (`loadAB` vs
`loadBA` × `bcast`/`gather`/`macc`); `gather` or `macc` may reuse B registers rather than holding a
full row live, and could be much closer to our own per-column-broadcast register profile. **This
plan does not yet know which reference variant is the fair comparison — checking all six live-
register counts per shape is step 1 of §4, before disassembling anything.** (Done: see §4.1 —
`macc` turned out to match this project's own register count exactly, on both shapes.)

**A same-kind experiment already produced a counter-intuitive result once.** At `32x7`
(a much smaller over/under-budget gap — exactly 32 of 32, zero spare, on both designs), [[0016]] §6
swapped the reference's real kernel into our harness, verified it bit-exact, and found the
reference's own equally register-constrained kernel ran **5-7% slower** than ours, not faster —
i.e. identical register pressure did not mean identical or worse performance for us. That result
does not transfer directly to 16x16/24x10 (those are far more over budget than 32x7 ever was, and on
the reference side may be a fundamentally different loading strategy, not just "more of the same"),
but it is the direct precedent for why this plan should not stop at "confirm both spill, therefore
that's the answer" — the same kernel-swap control is worth repeating here (§4.5).

## 3. What this plan does not decide

Whether to redesign `16x16`/`24x10` (or any tile) is out of scope, same boundary as [[0016]] §4.4 and
[[0017]] §4.5 — this plan only aims to find and document the cause of the performance gap, backed by
read assembly rather than register-count arithmetic alone.

## 4. The evaluation plan

### 4.1 Register-count audit across all six reference variants (no board time)

Before choosing which reference kernel to diff against ours, read the live-register count (same
counting method as §2: count declared `vfloat32m1_t` A/B/C registers at the compute nest's peak) for
all six `loadAB`/`loadBA` × `bcast`/`gather`/`macc` variants, at both `16x16` and `24x10`. Pick the
variant(s) whose register discipline is closest to ours (most likely `gather` or `macc`, which don't
need every B column resident at once) as the primary comparison target — this is the one used for
§4.3's source diff, §4.4's asm audit, and §4.5's swap control, since it isolates codegen quality from
register discipline, which is the question actually being asked (§1).

Grilled and resolved (2026-09-25): the *headline performance number* in §4.7 is not limited to this
picked variant. Report two reference numbers per shape, clearly labeled — the §4.1-picked variant as
the primary, structurally-fair number, and the reference's fastest-of-six as a secondary, best-case-
for-reference footnote (a plain benchmark number only, no source diff or asm work against it). This
guards against the same methodology trap issue #10 already found once in this project
([[project_benchmark_reference_comparison_trap]]): a reader mistaking a deliberately register-matched
comparison for "the reference's best."

**Done (2026-09-25).** Counted declared `vfloat32m1_t A_reg_*`/`B_reg_*`/`C_reg_*` (plus any
same-typed scratch, e.g. `B_tmp`) in each `gemm_RVV_<mr>x<nr>_b1_col_fp32` body, all six variants,
both shapes:

| shape | variant | A | B | C | total | spare (of 32) |
|---|---|---|---|---|---|---|
| 16x16 | `bcast` (loadAB and loadBA — identical) | 2 | 16 | 32 | 50 | −18 |
| 16x16 | `gather` (loadAB and loadBA — identical) | 2 | 17 (16 `B_reg_*` + `B_tmp`) | 32 | 51 | −19 |
| 16x16 | `macc` (loadAB and loadBA — identical) | 2 | 0 | 32 | 34 | −2 |
| 24x10 | `bcast` (loadAB and loadBA — identical) | 3 | 10 | 30 | 43 | −11 |
| 24x10 | `gather` (loadAB and loadBA — identical) | 3 | 11 (10 `B_reg_*` + `B_tmp`) | 30 | 44 | −12 |
| 24x10 | `macc` (loadAB and loadBA — identical) | 3 | 0 | 30 | 33 | −1 |

Two findings, neither anticipated going in:

1. **`loadAB` vs `loadBA` is not a register-pressure axis at all.** Every variant's declaration block
   is byte-identical between the two load orders (same line count, same line range; `diff` confirms
   the files differ elsewhere — presumably loop-body instruction order — but not here). The six
   variants collapse to three for register-count purposes.
2. **`macc` isn't merely "closest" to our design — its count is numerically identical.** `macc` holds
   no B broadcast registers live at all (it feeds `vfmacc.vf` a fresh scalar each time rather than a
   persistent broadcast register — the opposite of the line 135 guess above, which expected `gather`
   or `macc` to *reuse* registers within a still-declared B row, not to declare zero). Result: 34 at
   16x16, 33 at 24x10 — matching this project's own formula count (`(MR/8)×(1+NR)`, [[0017]] §2)
   exactly, both shapes. `gather` is not the middle ground guessed above either — it's worse than
   `bcast`, not better (51 and 44 vs. 50 and 43), from the extra `B_tmp` scratch register the gather
   path needs.

**This resolves §4.1's open choice: `macc` is the fair variant for both shapes**, used for §4.3's
source diff, §4.4's asm audit, and §4.5's swap control. `bcast` is the natural fastest-of-six
candidate for §4.7 (highest register count of the three, but no gather/scatter or per-element
scalar-broadcast overhead either); `gather` is dominated by `bcast` on registers with no offsetting
benefit, so it is recorded above but not tracked further.

### 4.3 Source-level side-by-side diff

For each shape, lay the generated compute kernel (`pj_gen/.../gemm_b{0,1}_xdsl.cpp` or `.mlir`)
next to the chosen reference variant's `gemm_RVV_<mr>x<nr>_b{0,1}_col_fp32` from §4.1. Compare:
register declarations and their live-range shape, loop structure (k-loop body), and — per [[0016]]
§6.4's finding at 32x7 — specifically check for the same kind of redundant loop-carried
`vfloat32m1_t vXXX = vYYY;` copy pattern [[0016]] found in our own generated code
(`gemm_b1_xdsl.cpp:201-224` there), since that pattern, not register count, was the more likely
explanation for 32x7's gap.

**Done (2026-09-25).** Generated both shapes locally (no board needed) via
`cd tests/pure_xdsl_blis_rvv && python3 generate_pure_blis_project.py --config
config_dim_sweep_16x16_24x10.json` — confirmed by reading `generate_pure_blis_project.py`'s CLI and
`config.py`'s output-dir naming (`fp32_<method>_vlen<vlen>_MR<mr>NR<nr>`, matching every existing
`pj_gen/` directory). Output landed at
`pj_gen/fp32_AXPY_FP32_Pack_vlen256_MR16NR16/gemm_b{0,1}_xdsl.cpp` and
`pj_gen/fp32_AXPY_FP32_Pack_vlen256_MR24NR10/gemm_b{0,1}_xdsl.cpp`. Diffed each against the §4.1-picked
`macc` variant: `ext/RVV_ukernels_benchmark/kernels/RVV_256_LDX/fp32/16x16/loadAB/macc/kernels_RVV_16x16_fp32.c:18503`
(`gemm_RVV_16x16_b1_col_fp32`, `:18355` for `b0`) and
`.../24x10/loadAB/macc/kernels_RVV_24x10_fp32.c:22241` (`gemm_RVV_24x10_b1_col_fp32`, `:22099` for `b0`).

**Register declarations match §4.1's count exactly at the source level**, on both sides: our
`gemm_b1_xdsl.cpp` for 16x16 declares 2 A-load temporaries (`v158`/`v161`, one per `MR/8` chunk) and 32
loop-carried `vfloat32m1_t` C accumulators (`v122`..`v153`) — 34 total, matching the reference's
`A_reg_0`/`A_reg_1` + 32 `C_reg_*_*` exactly. At 24x10: 3 A temporaries (`v158`/`v161`/`v164`) + 30 C
accumulators (`v124`..`v153`) = 33, again matching the reference 1:1.

**k-loop structure is the same shape and ordering on both sides**: one k-loop, column `j` outer
(0..NR-1) with `MR/8`-chunk `m` inner, one `vfmacc` per `(j, m)` pair per iteration, C stored
column-major. Neither side reorders the nest relative to the other.

**The redundant loop-carried copy pattern [[0016]] found at 32x7 recurs verbatim at both shapes, and
is the one real structural difference.** Our generated code declares a persistent "shadow" register
per C accumulator before the loop (`gemm_b1_xdsl.cpp:120-183` for 16x16, `:122-181` for 24x10, e.g.
`vfloat32m1_t v122; v122 = v29;`), then inside every k-iteration copies shadow-into-temp before each
`vfmacc` (`vfloat32m1_t v178 = v122;` at `:208` for 16x16, `:203` for 24x10) and copies the result back
out after all 32/30 `vfmacc`s finish (`v122 = v180;` at `:304`, `v124 = v177;` at `:293`). That's 32
extra copy-in + 32 extra copy-out plain assignment statements per k-iteration at 16x16 (30+30 at
24x10) that the reference's source does not have at all — the reference's `C_reg_i_j` accumulators are
assigned directly by the `vfmacc` call each iteration, no shadow variable, no copy. This is the same
MLIR→C++ lowering artifact [[0016]] §6.4 documented at 32x7, now confirmed present at two more
(and further over-budget) shapes.

**Surprising finding held for §4.4, not this section**: whether this noisier source costs anything once
compiled is not answerable from source alone — see §4.4, where it turns out not to.

### 4.4 Static asm/spill audit, both designs, both shapes (no board time)

Reuse [[0016]] §4.1's method exactly: compile each side's compute kernel to assembly
(`-O3 -march=rv64gcv -mabi=lp64d`), grep for `vs1r.v`/`vl1re32.v` (spill/reload) or any stack
`sd`/`ld` adjacent to the `vfmacc` block. Unlike [[0016]] (which only checked presence/absence at one
shape), this plan should **count** spill/reload instructions and estimate what fraction of the
compute-nest instruction count they represent, per design per shape — since §2 already predicts both
designs spill here, "does it spill" isn't the open question, "how much, and how costly" is.

**Done (2026-09-25).** Used the same cross compiler this project's other asm-spill work already uses
(`/opt/riscv/bin/riscv64-unknown-linux-gnu-gcc`, confirmed via `ref_baseline/run_ref_baseline.sh:38`
and issues [[0004]]/[[0006]]), same flags as [[0016]]: `-O3 -march=rv64gcv -mabi=lp64d -S`. Isolated
each side's compute kernel to a standalone compilable unit the same way [[0016]] §6.2 did: extracted
the reference's `macc` `b0`/`b1` functions verbatim from the two files above (renamed
`ref_gemm_RVV_<shape>_b{0,1}_col_fp32` to dodge symbol clashes), and compiled our own generated
`gemm_b{0,1}_xdsl.cpp` directly (it already `#include`s everything it needs via `gemm_headers.h`) —
8 compiles total (2 shapes x 2 betas x 2 designs), all clean, no warnings.

Grepped each compiled function body for `vs1r.v`/`vs2r.v`/`vs4r.v`/`vs8r.v` (spill-store) and
`vl1re32.v`/`vl2re32.v`/`vl4re32.v`/`vl8re32.v` (reload):

| shape | beta | side | spill-store | reload | total spill/reload | fn instr count |
|---|---|---|---|---|---|---|
| 16x16 | b1 | ours | 6 | 5 | 11 | 313 |
| 16x16 | b1 | reference (macc) | 6 | 5 | 11 | 325 |
| 16x16 | b0 | ours | — | — | 12 | 244 |
| 16x16 | b0 | reference (macc) | — | — | 12 | 256 |
| 24x10 | b1 | ours | 2 | 2 | 4 | 252 |
| 24x10 | b1 | reference (macc) | 2 | 2 | 4 | 253 |
| 24x10 | b0 | ours | — | — | 4 | 194 |
| 24x10 | b0 | reference (macc) | — | — | 4 | 198 |

**Both designs spill in practice at both shapes — Register Pressure does predict Spilling here.**
This settles the open question [[CONTEXT#Spilling]] flagged in §2: at 16x16/24x10 (both badly over the
32-register budget, unlike 32x7's exact-32 boundary case), the static over-budget count and the actual
emitted `vs1r.v`/`vl1re32.v` instructions agree.

**The spill counts are identical between our design and the reference's, on every shape/beta
combination checked** (11 vs 11, 12 vs 12, 4 vs 4, 4 vs 4) — not close, exactly equal. Located the
spill/reload instructions against each function's loop label (`.L3`/`.L10` .. `.L2`/`.L9`): for 16x16
`b1`, 6 of ours' 11 and 6 of the reference's 11 sit inside the k-loop body itself (the other 5 are
prologue/epilogue tile load/store spills, not loop-carried); for 24x10 `b1`, all 4 sit split 2-in-loop/
2-out-of-loop on both sides. As a fraction of the k-loop body's own instruction count: 16x16 is 6/77 =
7.8% (ours) vs 6/78 = 7.7% (reference); 24x10 is 2/54 = 3.7% on both sides. As a fraction of the whole
function: 16x16 is 11/313 = 3.5% (ours) vs 11/325 = 3.4% (reference); 24x10 is 4/252 = 1.6% (ours) vs
4/253 = 1.6% (reference). Every one of these fractions agrees to within rounding between the two
designs.

**The most surprising finding in this whole plan**: despite §4.3's redundant loop-carried copy pattern
(64 extra assignment statements per k-iteration at 16x16, 60 at 24x10, that the reference's source
doesn't have), our compiled function ends up with *fewer* total instructions than the reference's, not
more — 313 vs 325 at 16x16 `b1` (a 12-instruction, ~4% gap in our favor), 252 vs 253 at 24x10 `b1`
(near-identical). GCC's `-O3` optimizer evidently eliminates the shadow-copy pattern entirely as dead
code motion/copy propagation before register allocation ever sees it — it costs nothing in emitted
code, and doesn't add so much as one extra spill. This extends [[0016]] §6.4's finding (our 32x7 code,
identical register count, was never slower than the reference's own kernel) one level deeper: even with
a visibly noisier IR-lowering pattern in the source, and even at shapes far more over-budget than 32x7
ever was, our compiled compute kernel matches the reference's own Exo-generated kernel spill-for-spill,
instruction-for-instruction, at both 16x16 and 24x10.

**What this does and doesn't answer**: this confirms Spilling is real and roughly symmetric between
designs at these two shapes — if there is a performance gap between our design and the reference at
16x16/24x10 (not measured here, that's §4.5/§4.7's board work), it is very unlikely to be explained by
one side spilling more than the other in the compute kernel, since neither does. Packing-side cost
(§4.6, out of scope here) and anything downstream of this static compute-kernel view remain open.

### 4.5 Kernel-swap control (repeat of [[0016]] §6's method)

Grilled and resolved (2026-09-25): runs unconditionally for both shapes, not gated on the register
gap being "close enough" — 16x16/24x10 are already known (§2) to be far more over budget on both
sides than 32x7 ever was, so a strict "close enough" reading could skip this control for both shapes
by default, silently dropping the one experiment that already overturned an intuition once in this
project ([[0016]] §6's counter-intuitive 5-7% result at 32x7). A large gap makes a surprising result
*more* informative, not less, and the control is board-time-cheap relative to everything else here.

Scoped to the §4.1-picked fair variant only, not the fastest-of-six from §4.1's note above — the
question being asked (§1) is about xDSL codegen quality, not whether the reference's fastest loading
strategy is portable to this project's design (a legitimate but separate question, left for a future
issue rather than doubling the swap/verify work here).

Extract the chosen reference kernel, rename to avoid symbol clashes, splice it in behind our dispatch
call site (same technique as [[0016]] §6.2), verify bit-exact against synthetic packed buffers across
a few `kc`/`beta` values (§6.3's method) before trusting any speed number from it, then benchmark both
ways. This is what would show whether a perf gap (if any) is the tile's shared register pressure, or
something specific to one side's code generation — exactly the ambiguity [[0016]] §6.4/6.5 left
unresolved in the *other* direction (their generated code out-performing the reference's at equal
register count).

Bit-exact verification, §6.3's method: a standalone test binary on the board (not part of the normal

| shape | ours (baseline) | reference `macc`, spliced into our harness | Δ mean | Δ median |
|---|---|---|---|---|
| 16x16 | 3.92 / 3.92 GOPs (mean/median, 3 reps) | 3.91 / 3.91 GOPs (3 reps) | −0.3% (ours faster) | −0.3% (ours faster) |

designs spill identically at these shapes, this settles the swap-control's specific question: **the
compute kernel itself is not where our design loses ground to the reference, if it loses any at all** —
whatever the §4.7 head-to-head shows must come from packing, driver overhead, or something outside the
compute kernel, not from register-pressure-driven codegen quality.

### 4.6 Packing comparison — three-way, not four

The reference has no vectorized packing inside `RVV_256_LDX` itself, only its generic scalar
`pack_RB`/`pack_CB` in `gemm_blis.c` (outer harness, shape-agnostic). So the packing comparison is:
our vector pack vs. our scalar pack (already built in, toggled by `--scalar-pack`) vs. the
reference's one scalar pack — three variants, run through `run_pack_swap.sh --config
config_dim_sweep_16x16_24x10.json` for our two variants, and the reference's own harness
(`gemm_blis_family`, `run_ref_baseline.sh`) for its scalar pack, at the matching 2048³ input.

**Done (2026-09-25, board `jbpi`, core 4).** Ran `run_pack_swap.sh --config
config_dim_sweep_16x16_24x10.json --cpu 4 --tmin 10` unmodified — its own bracket (vector, scalar,
scalar, vector, four full builds) already covers "our vector pack vs. our scalar pack" at this exact
input:

| shape | vector GOPs (2 runs) | scalar GOPs (2 runs) | scalar vs vector | verdict |
|---|---|---|---|---|
| 16x16 | 3.88 / 3.88 (mean 3.88) | 3.89 / 3.87 (mean 3.88) | −0.0% | within noise |
| 24x10 | 6.25 / 6.25 (mean 6.25) | 6.24 / 6.24 (mean 6.24) | −0.1% | scalar pack slower (but by noise-level margin) |

**No measurable difference between our vector and scalar packers at this problem size, either shape.**
This differs sharply from this project's smaller-shape sweeps (B2/B3-class, where packing is a much
bigger fraction of total time) — at 2048³ the packed blocks (`mc×kc`/`kc×nc`, e.g. 768×128 or
578×170) are reused across a K-loop deep enough that compute dominates total time regardless of which
packer produced the block; packing cost shrinks to noise. This also directly explains why the §4.5
swap-control (which reused our own vector packer around both the original and the swapped-in reference
kernel) isolated compute-kernel differences cleanly — packing choice was never going to move that
number at this size.

The reference's own scalar pack is not run separately: it is *inherent* to its harness
(`gemm_blis_B3A2C0()`, the timed function in every `run_gemm.sh` call — `src/test_gemm.c:399-400`
confirms pack time is included in the timed region, unconditionally, since `RVV_256_LDX` has no other
packing path). So the reference's `macc`/`bcast` GOPs numbers in §4.7 below already are "reference
compute kernel + reference's own scalar pack," end to end — exactly the third leg of this three-way
comparison, without a separate run. Read against this section's own finding (packing cost is noise at
2048³ regardless of packer), any gap between our GOPs and the reference's macc GOPs in §4.7 is not a
packing-strategy artifact; it is dominated by the compute kernel and/or driver-level overhead outside
packing, which is what §4.5's swap control already showed is *not* where our kernel loses ground.

**The single most surprising number in this whole plan.** §4.1's plan text speculated `bcast` (highest
register count of the three variants, but no gather/scatter or scalar-broadcast overhead) might be a
"best-case-for-reference" footnote, faster in practice despite being worse on paper. The opposite
happened, by a wide margin: `bcast` is roughly **4x slower** than `macc` on both shapes (3.65→0.90 at
16x16, 6.45→1.45 at 24x10), not faster. This lines up with the register story, not against it: `bcast`
needs 16 (16x16) or 10 (24x10) B-broadcast vector registers live simultaneously (§4.1), 50/44 live
registers total against a 32-register budget — far worse than `macc`'s 34/33 — and `vfmacc.vf`'s
scalar-broadcast form (what `macc` uses) needs no persistent B vector register at all. `bcast` is not
"the reference's best variant that happens to look worse on paper" — it is genuinely, severely
register-bound in practice, exactly what its live-register count predicts. This also means the
secondary/footnote number this plan set out to report as a caution against over-reading the primary
number instead becomes evidence *for* the register-pressure story, just on the reference's side rather
than ours.

Board build notes worth recording for future runs at these shapes: native (on-board, not cross-)
compiles of the reference's per-shape kernel file (`kernels_RVV_<shape>_fp32.c`, ~300 lines for the
16x16/24x10 macc/bcast extract but part of a much larger ~18-45k-line multi-fringe-shape file) took
roughly 30-90s each at `-O3`, `bcast` noticeably longer than `macc` (more live registers, presumably
costlier register allocation) — using `nohup ...; disown` on the remote side and polling the log file
was necessary throughout (a client-side `timeout` around the double-hop ssh killed one in-progress
remote build outright, the exact pitfall [[0016]] §6.6 already documented).

**Putting §4.5-§4.7 together, against the user's original suspicion (does xDSL's own codegen
over-utilize registers relative to the reference at 16x16/24x10?):** every piece of evidence gathered
in this plan points the same way, and it is "no."
- §4.4: both designs spill identically (same count, same fraction of instructions, same in-loop vs.
  prologue split) at both shapes — register pressure is a shared property of the tile, not something
  our lowering does worse.
- §4.5: with the compute kernel controlled for (our own harness, our own packer, only the microkernel
  swapped), our kernel is a wash (16x16) or mildly faster (24x10, −0.9 to −1.4%) than the reference's
  own equally register-constrained `macc` kernel.
- §4.6: packing strategy (vector vs. scalar, ours vs. the reference's only option) makes no measurable
  difference at this problem size, so it cannot be hiding a packing-side penalty behind the head-to-head
  numbers below.
- §4.7 head-to-head: against the fair, register-matched reference number, we are 7.4% faster at 16x16
  and 1.6% slower at 24x10 — a small, shape-dependent split, not a one-sided pattern, and nowhere near
  the scale a real register-overutilization problem would produce (compare to `bcast`'s 4.4x, from a
  kernel that *is* badly register-bound in practice).

**The 24x10 −1.6% head-to-head gap is real but unexplained by anything measured here** — it does not
appear in the §4.5 swap control (same compute kernel, our harness: ours was *faster* there), so it is
not the compute kernel; §4.6 rules out packing strategy. The remaining candidates are driver-level
overhead differences between the two harnesses (our C++ driver vs. the reference's C `test_gemm.c`) or
something in how each side's outer M/N/K loop nest is structured around the microkernel — neither
measured by this plan, and small enough (1.6%) that it may not be worth a dedicated follow-up. Recorded
here rather than chased further, since it is far outside the scale of "register overutilization" the
plan was opened to check, and chasing driver-level constant-factor differences is a different question
from the one this issue asked.

## 5. What this plan cannot show

- §4.1/§4.3's register counts and source diff are static (source-level or pre-backend-allocation) —
  same limit [[0016]] §5 and [[0017]] §5 already noted: they show what was emitted, not for certain
  what the backend compiler's own allocator does with it. §4.4's actual disassembly is what closes
  that gap, but only for the compute kernel, not the packing code (out of scope here).
- This plan picks one reference variant per shape (§4.1) as "the fair comparison" — the other five
  variants per shape are read for their register counts only, not benchmarked or diffed line-by-line,
  unless §4.1 finds more than one candidate close enough to warrant it.
- Board time and time-of-day are not controlled between the xDSL-side and reference-side runs beyond
  running them the same day and same (idle) core — same caveat as every other cross-run comparison in
  this project ([[0014]] §6).
- This plan does not decide whether 16x16/24x10 should ever ship as real tile choices — per §3, that
  redesign question is explicitly deferred.
